This map describes the browser source in `src/app/`. `SiteApplication` is the current static-site SPA owner; feature controllers below it are page behaviors and can be mounted independently after their markup exists. Selectors are the component contracts in the source, not proposed WordPress class names.

## Reuse boundaries and porting notes

Foundation implementation: `superworld-core/assets/js/parts-table.js` adapts the series table's selection, search, filtering and pagination into a per-root WordPress component. It uses server-rendered columns and WordPress REST rather than the SPA renderer; full Specification Search, calculators and original seven-column page layout remain future work. Frontend extensionless Specification Search proxy routes in the inventory map to the backend `.php` endpoints documented in `PUBLIC_API_V1.md`.

- `SiteApplication` owns client-side URL routing, fixed-page replacement, shared chrome, metadata, and Inquiry resolution. WordPress already owns those concerns, so porting it would create two route and render owners. Keep Elementor responsible for page structure and mount individual controllers against stable roots.
- `SiteInteractions` and `SiteEnhancements` are aggregators, not single widgets. They initialize broad selector sets on every SPA render. For WordPress, expose narrower per-root mounts so unrelated Elementor sections do not install global listeners or require all site markup.
- Reusable behavior is concentrated in `CarouselWidget`, the isolated Specification Search app, and the product API client. `ProductPages` itself remains coupled to the supplied catalog HTML and A4K selectors; port the API client/data mapping separately from its current renderer.
- Page styles are currently bundled under `src/styles.scss`; Specification Search is a separate CSS entry. WordPress enqueueing should preserve the separate search bundle and load page/component styles only where needed. Avoid copying compiled styles as Elementor custom CSS: several selectors depend on `#app` and the spec-search wrapper scoping contract.
- Most interaction controllers bind listeners directly to rendered page nodes; removal of the route tree lets those nodes and closures be collected. Explicit cleanup still matters for document/window listeners, observers, intervals, RAFs and in-flight requests. WordPress pages persist across widget updates, so mount/unmount must be explicit for all retained widgets.
